# App and research release coherence

The map and research page must agree on reviewed presence in every compatibility-publication state. Alabama is currently authoritative; the remaining configured states retain the documented research-only migration boundary.

Run `npm run check:release-coherence` before uploading new app bundles or pushing a build-relevant release. This read-only check compares generated explorer species IDs for every authoritative county with `verified-present` pairs in the currently published R2 research release. It compares species identities, not just totals or ordinal positions. Missing county scope, duplicate species, invalid ordinals, inconsistent state identity, unavailable files, incorrect sizes or hashes, and a changing release pointer hold the release.

The check reads `current.json`, verifies the immutable manifest against its SHA-256, verifies each county object against its decoded byte length and SHA-256, and reads the pointer again. Requests are restricted to the existing public `https://data.isitusa.com` origin, without credentials or redirects. The budget is two concurrent requests, at most 128 authoritative counties, 256 MiB decoded overall, 16 MiB per manifest, 20 MiB per county, 15 seconds per request, and 90 seconds for the entire check. Alabama needs 70 GET requests, including both pointer reads. Expanding authoritative publication requires reviewing these explicit limits. This operation has no uploads, storage writes, pointer promotions, deletions, or paid-resource creation.

The Vercel ignored-build command holds an incompatible release before the full build starts. Research-only, operations-only, and documentation-only changes keep the existing skip behavior. If Git classification is unavailable, the coherence check still runs before allowing a hosted build. A provider failure holds the build instead of treating unverifiable data as compatible.

`npm run build` also runs the guard before preparing assets or pruning the disposable Vercel workspace. Hosted production and preview builds are checked, because a preview can later be promoted. Normal local builds remain available for reviewing queued research changes. `npm run check:vercel-publish` includes offline regression tests for identity comparisons, corrupt or missing content, scope differences, provider failures, pointer races, and both build entry points.

A passing check proves compatibility with the pointer observed during that check. It does not guarantee that the mutable pointer will remain unchanged after the build. MAIN must coordinate the app and research publication, repeat the check immediately before a separate promotion, and verify both live routes and the active alias after publication. Promoting previously built deployments does not rerun their build commands. If publication exposes disagreement, restore a compatible app/research combination and retain an incident receipt. Do not bypass the seven-day research publication cadence simply to make a premature app release pass.

The September 8, 2026 r18 incident illustrates the boundary. Valid research added Common Carp to Talladega County's generated map, but the public research pointer still served the previous unresolved result. The app release was rolled back. All 480 net unique determinations remain committed and verified; their national research release remains queued. The uploaded immutable app bundles remain retained. The guard holds that candidate until publication can be made coherent. See `ops/releases/epa-wqp-rollback-20260908-r18.json` for the dated evidence and rollback identity.

Vercel documents that ignored-build exit code 0 cancels a build and exit code 1 continues it. A canceled build still counts toward deployment quotas, so this guard supplements meaningful release batching: https://vercel.com/docs/project-configuration/project-settings#ignored-build-step (checked September 8, 2026).
